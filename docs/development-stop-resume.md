# Explicit development stop and resume

Normal desktop pause/resume and Drafted's `upkeep pause|resume --request-key` record a durable development intent on the original task primary. The desktop resolves the configured immutable runtime capability and immediately runs that same CLI with the recorded key. An interrupted cancellation retries only that intent for a bounded 30 seconds; an unsettled family remains truthfully pending for the existing upkeep pass. This adds no primary, scheduler or approval prompt.

The local desktop uses its bundled management code: activating these controls requires an updated desktop bundle and normal app restart (or restarting `desktop:dev` against this source). Updating only the server and tooling does not update an already-running old desktop. Remote host operations use the updated host checkout; the reviewed host CLI and upkeep paths are available independently. Tasks without a primary, worktree or resources retain the existing automation-only pause/resume path.

Raw `POST /api/tasks/:id/automation` requests with only `action: pause|resume` retain their maintenance behavior. They never create, supersede or infer a compute intent. A maintenance unpause after a completed stop does not start apps.

Explicit requests add `development: true` and a stable `requestKey`. Review handoff uses `action: stop-development` with the exact ready review resource key and identity digest. The review must be a separately owned, leased runtime/native app; the tooling independently verifies its saved representative health checks before recording the handoff and each stop boundary. A prepared Git checkout alone is not app readiness.

The additive task `developmentIntent` projection is saved status, not effect authority. The existing metadata journal binds original primary, source ownership, branch and policy pin. `development-authority` renews that exact revision/digest and selected compute identities. The client adapters independently check their process/container/recipe identities before effects. `development-complete` accepts only the current complete compute membership and resource epoch; it never releases a resource or proves deletion. New material or changed ownership makes completion pending again.

Paused stops wait for owned agent work to settle. Their narrow Allocated acknowledgment preserves immutable receipt metadata; data, review, public routes and owner instructions remain intact. Resume refuses current cleanup authority or cleanup provider transport. Existing explicit revocation/non-merge work contracts and return-to-work transitions remain authoritative; historical cleanup records are preserved. After that transition, the same original compute may acknowledge Ready, with only the runtime's strict existing progress field permitted to change. Recipe, provider, container, network and volume identity stay exact; Released resources never resume. A later opposite intent prevents stale cancellation or service effects.

When cleanup supersedes a completed resume or review handoff, the saved intent becomes non-actionable in task projection so its changed resource epoch cannot obstruct cleanup retries. Explicit owner-pause stop remains available during cleanup. The immutable intent history remains recorded.

Saved Docker/native/runtime recipes resume their existing instances without provisioning or seeding. Historical source-only native recipes support independently verified stop, but cannot invent a restart recipe: their explicit resume remains pending with a concrete unsupported-adapter result.

Validation includes real route/client Docker stop/resume with lost effect/completion responses, actual saved-runtime resume after cleanup revocation with progress and lost Ready acknowledgment, a real three-process legacy family interrupted after its first exit, true opposite-intent transaction interleavings, original identity and active-writer refusal, exact review lease/membership, private-socket desktop invocation of a committed runtime CLI under Electron using the host's Bun executable, changed capability refusal, and unchanged raw maintenance pause semantics. Fixtures preserve saved data and separate review, and perform no live task effects.
