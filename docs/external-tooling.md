# External tooling and managed tasks

An optional machine repository entry `tooling: { root, ref }` selects another Git repository for policy and skills. The target `root` and `worktreeRoot` continue to own product checkouts and ACP cwd validation. Policy is read from `.remote-agent.config.json` at the resolved commit; dirty source changes do not apply. The default remains repo-owned tooling.

The external policy may set `baseBranch` (for example `origin/staging`) and `preparation: "agent"`. Remote Agent creates the worktree before starting its primary agent. Skill Composer runs from the pinned tooling checkout with its own dependencies and writes generated skills through its supported output-directory overrides. Narrow local Git excludes keep those generated folders out of product PRs.

When external tooling includes `AGENTS.md`, its contents are included directly
in the task message with the pinned source path. This delivers owner-configured
task exceptions alongside the request instead of relying on a skill file to
override the target repository's general instructions. Composition-based
workflow continuations and composition-failure repair prompts retain that
policy. Repositories without external tooling keep their existing prompts.
The mutable tooling source and the target's tracked instruction files are not
rewritten. This is instruction delivery, not a permission or sandbox bypass;
actual task control and provider approval restrictions still apply.

A remote branch base is fetched before each new launch resolves its commit. Fetch errors block creation, even when a cached tracking ref exists. Parallel launches can share an in-flight fetch, but no result is cached for later launches. The task persists the resulting `baseCommit` before creating its worktree; retries use that recorded commit without refetching or changing existing work. Local branch names and explicit commit revisions continue to use the caller-selected local state. The configured target clone is never pulled, checked out or reset as part of this process.

The server coordinates its `git worktree add` commands by the canonical common
Git directory, including linked checkouts and path aliases. Git reads neighboring
registrations during creation, so concurrent additions can otherwise observe an
unfinished `commondir` file. Only registration is queued: independent repositories
and repository bootstrap remain concurrent, and each request keeps its resolved
base commit. A failed addition still fails its caller and releases the queue for
later requests; it does not remove or repair existing branches or worktrees.

`RemoteTask` is created before setup and retains its request key, host, target branch/base, worktree, pinned tooling revision, primary session, environment status and resource receipts. Retrying the same request reuses that identity. Setup failures remain visible; both direct and workflow launches can start a repair agent in the already-created worktree. Unknown worktrees are not adopted. A resource key cannot be reassigned to a different external resource.

The pinned acpx 0.13.2 dependency needs the committed Bun patch to preserve uppercase environment variable names in session records. Its persisted-key validator otherwise rejects `session_options.env`, preventing a real session from launching. The patch treats only that map as opaque; the rest of the validator stays active. A regression test saves and reloads the actual installed store. Remove the patch only after an upstream version passes that test.

The authenticated `/api/tasks` API lists, inspects and starts tasks. POST takes `requestKey`, `repositoryId`, `branchName`, `prompt`, and optional `provider`. The session's MCP adds `inspect_task`, `report_task`, `register_resource` and `publish_plan`. The latter works with both providers and preserves the source issue's description; it does not automatically transition the issue.

Workflow launches and follow-ups carry the issue description. `read_source_issue` refreshes the current issue context without giving the provider a Linear credential. `ask_question` posts only to the session's linked issue and registers its reply thread before posting. A persisted UUID identifies the comment; retrying the same `requestKey` reconciles uncertain delivery without another comment. A different body or issue under the same key is rejected. Answered threads stay answered during reconciliation. Live delivery needs an automation identity distinct from the owner (a private Linear app or separate account), with owner-restricted webhook routing.

A session with no active issue link receives HTTP 404 with `code: "no_linked_issue"` from `GET /api/sessions/:sessionId/source-issue`. The MCP caller reports the accompanying explanation and directs it to `inspect_task` for supported task context. This covers tasks originally started without an issue and does not restore ended links or authorize issue-dependent operations. Missing/closed sessions, network authorization failures and actual provider failures retain their existing error paths.

User restrictions use existing connection repository-routing conditions. Configure `linear.userId` alongside the exact organization/team identity in the same AND-group. For Issue events it is the envelope actor; for Comment and Reaction events it is the author. Missing identity fails to match. Issue assignee/creator identity never substitutes for the acting user. Do not use a wildcard subscription for an owner-only deployment. A separate automation identity is still necessary for user-authored comments if `agentUserId` self-loop suppression would otherwise identify the human as the agent.

Human control transitions through draining → human → paused or explicit resume. Immediate ACP turns are rejected while control is not agent, including delegates in the same worktree. Linear and owner instructions persist in `RuntimeInstruction` and wait until explicit resume. The grant waits for active sessions to stop. On server restart, outstanding control remains paused. Control coordination assumes agents use the managed browser gateway; it is not an OS sandbox against arbitrary same-user processes. Detached commands and application-specific background jobs need live acceptance before a task may be declared safe to take over.

## Owner supervision and delivery

`apps/server/mcp/owner-mcp.ts --socket PATH` exposes owner-only stdio tools over the private control socket. Connect it through the owner's SSH identity. It lists tasks and placements, reads actual transcripts and questions, launches on an explicit host, queues instructions, answers questions, and pauses/resumes/closes work. It is intentionally separate from the narrower MCP injected into task agents. Closing work retains files and preview leases; resource cleanup belongs to the external tooling adapter. This is a supported supervision interface, not a native Codex import of an acpx transcript.

### Outcome recovery and completion

Owner comments on a managed source issue and registered direct children now enter the existing primary's durable inbox. They do not require a mention or a new routing/model call. Owner-paused work remains queued until the owner resumes it. `read_work_graph` binds current direct children; `publish_child_issue_update` reconciles only those acceptance units and checks dependencies. Parent handoff refuses unfinished children; Manual Review may retain explicitly reported Blocked units or verified children awaiting owner acceptance. A child in Manual Review needs its latest successful publication from the same owning primary and connection to request Manual Review, with the comment and all selected evidence uploaded and attached. Merge/Done still require completed/canceled children and their existing delivery checks.

This review exception reuses existing published receipts without rewriting them or requiring a new observer field. A child currently reopened or with a later published non-review update does not qualify. Unrelated provider title/label/comment changes do not invalidate review, and an owner returning an otherwise verified child to Manual Review is respected. The guard does not infer verification from the status alone or judge evidence from prose. It checks the normal publication's completion; it does not independently rerun product verification or reconstruct every external status transition. Parent retries preserve the original comment UUID, and completed retries do not rewind later owner changes. No child, session, preview or environment is closed by review publication.

DRA-157 acceptance uses the normal child and parent HTTP routes, including a real Unix socket, disposable SQLite, actual image validation/upload receipts and a substituted provider. The historical DRA-99 replay is superseded and was not performed because that product work is already Done and cleanup is underway. Tests reproduce the original 409 before the fix and cover same-key restart, lost comment acknowledgment, partial evidence, Todo/reopened/later-unverified children, foreign receipts, late state changes and unchanged Merge/Done guards.

Configured owner Merge transitions record completion authority and acceptance of the task's actual content automatically. No extra approval API call is required for that normal path. Commit, remote publication, PR, review and merge are independently observed; reporting a successful turn cannot manufacture delivery. Explicit local/research boundaries are supported without forcing a PR. For exceptional owner decisions, `owner-mcp.ts --socket PATH --config FILE` enables authenticated completion-contract and verification writes using the config's API key. These writes require bearer authentication even on the local control socket and are not session tools. Do not use them to fabricate a missing approval or verification result.

Finalization is two-phase: the task-bound adapter prepares a success-only delivery receipt before cleanup, removes exact owned resources and the clean worktree, asks the server to confirm filesystem/Git absence against that receipt, publishes Done, then closes the primary last. A missing checkout without both receipts is not successful completion. Interrupted cleanup and publication reuse stable keys; no broad Git pruning, closed-session bypass or repeated blind deletion is needed.

Old pins can resolve named capabilities from `.remote-agent-capabilities.json` at the owner-configured committed host tooling revision. This preserves the original task pin and records separate immutable provenance. Session tools expose only `development-credentials`, returning instructions/adapter references, never secret values or automatic export. Preparation and owner-authorized Merge use internal bounded compatibility paths. Mutable source edits are not release capabilities.

Interrupted delivery remains unknown until the exact provider process is proven stopped and its effects inspected. Supported instruction resolution is idempotent and gives an authorized retry a new lifecycle identity; it never blindly replays an uncertain effect. Activity inspection separates actual in-process execution from persisted active state, queued work, owner waits, control state and delivery uncertainty. It does not resume work or invent an ETA.

Known projection failures use a durable per-event retry budget: five failed attempts with exponential backoff. Exhaustion retains the original journal event and inbox identity; unrelated sessions continue. After inspecting and correcting the cause, the authenticated owner can request `POST /api/tasks/:taskId/projection-retries` with `{sessionId, eventId, stage, requestKey, reason}`. `stage` is `notify`, `project` or `stall`. Only an exhausted delivery owned by this open, agent-controlled task can be reset. A stable request key cannot replenish a later exhausted cycle. This retries idempotent projection work, not a provider turn, and never resumes paused control. Pending/exhausted delivery receipts remain visible in task activity.

Direct tasks can call `ask_question` without a Linear link. The question persists locally for owner supervision. Answering persists one instruction atomically with the answered state; repeated identical answers are safe and changed answers are rejected. Linked questions still use their fixed Linear comment UUID.

`RuntimeInstruction` stores an instruction before a provider call, waits during active work or an explicit owner pause, and records delivery outcomes. After interruption, a terminal provider event can settle the receipt. An uncertain turn blocks later instructions until the owner inspects history and explicitly acknowledges, cancels, or retries it with a reason. It never automatically replays an uncertain agent action. The migration marks earlier launches as legacy receipts to avoid replaying existing tasks.

Optional `machine.acpx.maxConcurrentTurns` bounds simultaneous managed provider turns on one host. Omission remains unlimited. A FIFO admission queue waits before provider startup; a durable instruction remains queued until both admission and handle creation succeed. Cancellation, task control changes, session closure and shutdown cancel waiting admission. A failed startup cannot reopen a closed session. Direct ACP requests waiting in a disconnected client are not a durable inbox; only persisted Linear/owner instructions have the described restart recovery. This limit does not constrain application containers or detached processes.

`delegate_session` accepts an explicit provider/model and optional `notifyParent: true`. Opted-in workers use the durable inbox for their first turn, stay available for follow-up, and return each completed, failed or cancelled turn to the parent's inbox. Lifecycle-journal replay reconciles the same result identity; an explicit owner pause holds both worker instructions and returned results. Existing one-shot delegates are unchanged. `inspect_delegates` reads only the caller's children, their actual configuration, recent history and receipt metadata; `instruct_delegate` queues a follow-up to the same child with a stable request key. Parents should end their turn while a worker runs to release their provider slot, then inspect its result and work before continuing. Delegates share the parent's worktree, so parallel writers need disjoint scope. Model choice, availability fallback and browser-verification responsibility belong in the external tooling skill.

## Explicit host placement

Optional `routing` config supports `ingress`, `receiverOnly`, `peers` (endpoint, private API key and repository allowlist), and `connectionHosts`. The desktop Machine page edits the same schema through its normal explicit save flow. Configure one Linear ingress. Receiving hosts use authenticated forwarding and retain their exact owner filters. Peer endpoints require HTTPS or loopback SSH forwarding; no credentials are embedded in URLs. No automatic migration, load balancing or capacity guarantee is implied.

`POST /api/routing/launches` persists `TaskPlacement` and `TaskDelivery` before dispatch. The recipient receives a stable launch identity. Lost acknowledgements retry that identity on the same recorded host. Instructions and owner actions stay ordered behind launch delivery. Unavailable owners remain recorded, and removing a peer does not move or delete its tasks. Linear issue placement can be selected before dispatch through `/api/routing/linear-placement`; otherwise the configured connection host is used. Replies retain the issue's existing placement. `/api/routing/placements/:id` resolves Linear task identity from the recorded owner and exposes actual activity when reachable.

Signature, freshness and owner checks happen before ingress persistence. The authenticated forwarding route rechecks owner/repository eligibility but does not reject a properly accepted queued event merely because it aged during an outage. Only the ingress should have a public Linear webhook.

The migrations are additive. Snapshot the runtime database/config with connections closed before deployment. The MacBook Air pilot uses separate state and service identities, preserving the existing Cubic installation.

Browser viewers do not own task execution. `ownerPaused` preserves explicit owner pauses; the authenticated automation endpoint retains pause/resume/close. The task read/list/progress responses temporarily project legacy `controlMode` and `controllerId` values for already-pinned tooling: open tasks are `agent`/null, owner-paused or closed tasks are `paused`/`task-supervisor:<id>`. These fields are not stored and the browser-control endpoint no longer exists. Existing pins can inspect and clean up their own tasks without a silent policy upgrade.

Missing legacy mappings do not gate cleanup or change task ownership.
